Working principle

Build what is needed. Make it maintainable.

The amount of planning, testing, and documentation should fit the system and the risks involved. A small website and a complex application do not need identical processes.

01 / Project stages

From the first discussion to delivery.

These four stages describe a typical project. The details change with the size and type of work.

01

Understand the need

Discuss the current problem, intended users, existing systems, constraints, and the result that would make the work useful.

Typical result: A shared description of the problem and goals.

02

Define the scope

Identify deliverables, necessary features, assumptions, responsibilities, and work that is outside the initial project.

Typical result: An agreed scope and proposed approach.

03

Build and review

Implement the agreed work, test important behavior, and review progress at points that make sense for the project.

Typical result: Tested work that can be reviewed against the scope.

04

Deliver and support

Deliver the agreed files, application, website, or system changes. Confirm handoff needs and discuss any further support separately.

Typical result: Agreed deliverables and a clear next step.

02 / Scope and expectations

Decide what is included before work starts.

A starting price or early discussion is not a complete project agreement. The intended result, expected features, and important exclusions should be clear before implementation begins.

New requests can arise during development. When they affect the agreed scope, their effect on cost or delivery should be considered before the extra work begins.

Review services and starting prices

Items to establish during scoping

  • Project goals and intended users
  • Features and deliverables
  • Existing services, accounts, and integrations
  • Client-provided material and access
  • Testing and review expectations
  • Schedule, price, and work outside the scope
  • Handoff, hosting, and support responsibilities
03 / Different kinds of work

One approach, adapted to the job.

We can use the same basic stages without forcing every engagement into one fixed plan.

New websites and applications

Start with users, content, and required behavior. Define the first useful release before adding optional features.

Existing systems

Review the current behavior and constraints before changing code. Focus on the identified defect, improvement, or integration.

Contract and subcontract work

Fit the work into the agreed responsibilities, technical standards, communication methods, and delivery requirements of the engagement.
